# Registre de parité Swimmich — client mobile Immich v3.4.0

Cible de parité : le client mobile officiel Immich **v3.4.0** (2026-11-10, dernière version stable ; v3.3.0 : 2026-10-07 ; v3.3.2 n'apparaît pas dans l'API des releases). Date d'audit : **2026-11-11**. Sources : le dépôt `immich-app/immich` au tag `v3.4.0` (`mobile/lib/**`, `open-api/immich-openapi-specs.json`), les notes de version GitHub v3.2.0 à v3.4.0, la référence locale `docs/mobile-features-vs-flutter.md` (§1 à §26) et le code de Swimmich lu le même jour. Les écarts d'interface se mesurent à une double référence : le parcours et les retours d'état du client officiel, puis le design system du dépôt (`Sources/DesignSystem/`) et les règles Apple (HIG).

Vocabulaire. Statut d'une fonction : `présent`, `partiel`, `absent` ou `hors périmètre`. Une preuve amont s'écrit `mobile/lib/<chemin>[:ligne]@v3.4.0`, `PR #<n> (vX.Y.Z)`, `docs §<n>` ou `Recherche négative : <motif> sur <chemins> → 0`. Une preuve locale est un `chemin:ligne` du dépôt ; pour `absent`, c'est le `chemin:ligne` qui montre le manque ou une recherche locale (la mention « Recherche locale : », le motif `grep -E` entre accents graves, « sur », des chemins, puis « → 0 ») que le script rejoue. Un `Exclu : <raison>` justifie une exclusion. Chaque écart renvoie à un besoin `B-<n>`, et chaque besoin à un lot de la section C. Un constat noté « non vérifié à l'exécution » vient de la lecture du code, sans simulateur. Le contrôle se lance par `Scripts/check-parity-registry.sh [AC-1|AC-2|AC-3|AC-4|AC-38|all]` ; un lot qui se livre passe sa ligne de C à `livré` (SHA, AC), met à jour les lignes de A et B qu'il ferme, puis relance `Scripts/check-parity-registry.sh all`.
