> **Audit 2026-09-15 — écart G4** (`.omp/backlog/ImmichSwiftUI-backlog.md:779`) : le client Flutter a un écran dédié au statut de synchronisation — `mobile/lib/pages/settings/sync_status.page.dart` (26 lignes, `SyncStatusPage` → `SyncStatusAndActions`), atteint par la route `SyncStatusRoute` (`mobile/lib/routing/router.dart:182`, `AutoRoute(page: SyncStatusRoute.page, guards: [_duplicateGuard])`) depuis la tuile `SettingSection.beta` de `mobile/lib/pages/common/settings.page.dart:100` (`context.pushRoute(const SyncStatusRoute())`). Côté iOS, aucun écran n'agrège l'état local : les compteurs du ledger et la dernière confrontation serveur vivent dans une section de `BackupSettingsView` (`Sources/Features/Upload/UploadViewModel.swift:495-544`), la progression du run dans une autre (`:651-919`), et l'index hors-ligne nulle part à côté du backup (`Sources/Features/Offline/OfflineAssetsView.swift` ne montre que lui-même). Rien ne relie « suivis / en attente / en échec / hors-ligne » sur une seule surface.

**Objectif** : après cette fiche, l'utilisateur ouvre « Sync Status » depuis le bouton de barre posé à côté de l'avatar de profil (chaque onglet en porte un) et lit en une seule vue l'état réel de la synchronisation locale : combien d'assets le ledger tient pour sauvegardés, combien sont encore en attente dans le run courant, combien sont prêts à partir (file d'upload), combien ont échoué, combien sont épinglés hors-ligne et pour quel volume, quand le run a eu lieu pour la dernière fois et quand le ledger a été confronté au serveur. Il peut relancer un run, l'interrompre, confronter le ledger au serveur, vider le ledger et purger le cache hors-ligne — sans changer d'écran.

**Hors périmètre** :
- L'écran de détail **par asset** d'un run (état, erreur, retry d'un asset précis) : c'est l'écart G5, bande AC-5040–5049 (`upload-detail`). Ici les échecs ne sont listés que par nom + raison, en lecture, via `BackupEngine.failures`.
- **L'export de la base locale et sa réinitialisation** (`export_database`, `reset_sqlite` de `SyncStatusAndActions`) : ces deux actions n'existent que parce que le Flutter tient une réplique Drift. iOS n'a pas de base locale d'assets ; les équivalents réels sont la purge du ledger et la purge du cache hors-ligne, qui sont dans le périmètre.
- Les **jobs `sync_local` / `sync_remote` / `sync_cloud_ids` / `hash_asset`** : ils répliquent la réplique Drift via `POST /api/sync/stream` et hachent en masse pour alimenter cette réplique. iOS n'a ni réplique ni job de hachage séparé — le hachage est une étape interne de `BackupEngine.run()` (`Sources/Services/BackupEngine.swift:240-300`). Le seul job local est donc le run de sauvegarde lui-même.
- La **réparation** d'un ledger incohérent ou d'un index hors-ligne désynchronisé : l'index se réconcilie déjà seul au chargement (`Sources/Services/OfflineAssetStore.swift:296-320`), le ledger se réconcilie par `reconcileNow()`. Aucun écran de réparation n'est ajouté.
- L'import d'une **couleur de statut** ou d'un nouveau composant DesignSystem : l'écran réutilise `PVStatusBadge` et les tokens existants.

**Hypothèses** (vérifiées dans le dépôt et contre `immich-app/immich@main` = `e55ac299`, le 2026-09-15) :

**Approche retenue** : A — un `SyncStatusViewModel` (`@MainActor @Observable`) qui **compose** les deux ViewModels de processus déjà existants (`UploadViewModel` pour le ledger + le moteur, `OfflineDownloadViewModel` pour l'index hors-ligne) et n'ajoute aucun état propre, plus une `SyncStatusView` stateless poussée depuis la section Management de `ProfileView`.
- **B (rejetée)** : ajouter une section « Sync status » à `BackupSettingsView` au lieu d'un écran → rejetée pour deux raisons mesurables. (1) Périmètre : l'écran doit couvrir l'index hors-ligne et sa purge, qui n'appartiennent à aucun écran de backup — `BackupSettingsView` ne connaît pas `OfflineDownloadViewModel`. (2) Lisibilité : `BackupSettingsView` porte déjà la progression vivante du run (`progressSection`, `activeProgress`, `currentItemRow`, `segmentBar`, `completionSummary` — `UploadViewModel.swift:651-919`, ~270 lignes) ; y imbriquer l'état durable (ledger, dernière exécution, index hors-ligne) mélange « ce qui se passe maintenant » et « ce que l'appareil contient », et l'upstream garde précisément ces deux surfaces séparées (`SettingSection.backup` vs `SettingSection.beta`).
- **C (rejetée)** : un `SyncStatusViewModel` autonome qui reçoit directement `any BackupLedgerStoring`, `OfflineAssetStore` et un `BackupEngine` neuf → rejetée parce que le dénominateur d'un run (`total`) n'est connu que de l'engine qui l'exécute : un second engine afficherait « 0 en attente » pendant qu'un run est en cours dans `container.upload`, et deux engines se disputent la Live Activity (le commentaire du champ `upload` de `DependencyContainer` documente ce bug). `BackupLedger` et `OfflineAssetStore` sont, eux, déjà partagés — les relire directement ne sert à rien.

## Étapes

1. **Le ViewModel d'agrégation** — NEW `Sources/Features/SyncStatus/SyncStatusViewModel.swift` : `import Foundation`, `import Observation`. Aucun état stocké : **toutes** les propriétés sont des projections calculées.
   - Compteurs du ledger et du run : `var trackedCount: Int { upload.trackedAssetCount }`, `var pendingCount: Int { max(0, upload.engine.total - upload.engine.processedCount) }`, `var stagedCount: Int { upload.engine.stagedCount }`, `var uploadedCount: Int`, `var alreadyOnServerCount: Int { upload.engine.rejectedCount }`, `var failedCount: Int`, `var deferredCount: Int`, `var waitingForWiFi: Bool { upload.engine.deferralReason.contains(.waitingForWiFi) }`, `var waitingForICloud: Bool { upload.engine.deferralReason.contains(.waitingForICloud) }`, `var failures: [BackupFailure] { upload.engine.failures }`, `var currentFileName: String? { upload.engine.currentFileName }`.
   - Index hors-ligne : `var offlineCount: Int { offline.cachedAssets.count }`, `var offlineBytes: Int64 { offline.cacheUsage }`, `func formattedOfflineBytes() -> String { offline.formattedUsage(offline.cacheUsage) }`.
   - Exécutions : `var phase: BackupEngine.Phase { upload.engine.phase }`, `var isRunning: Bool { upload.running }`, `var isCancelling: Bool { upload.engine.isCancelling }`, `var progressFraction: Double { upload.engine.progressFraction }`, `var lastRun: UploadHistoryEntry? { upload.uploadHistory.last }`, `var lastServerCheck: Date? { upload.lastReconciliation }`.

## Incertitudes à lever à l'implémentation

- **Le libellé exact du bouton de barre.** `.accessibilityLabel("Sync Status")` retient le vocabulaire de l'upstream (`t.sync_status`) ; si l'extraction i18n du dépôt a déjà une clé proche, la réutiliser plutôt que d'en créer une. Vérifier par : `python3 -c "import json;d=json.load(open('Resources/Localizable.xcstrings'));print([k for k in d['strings'] if 'ync' in k or 'Status' in k])"`.
- **L'icône du bouton de barre.** `arrow.triangle.2.circlepath` avait été retenu le 2026-09-15 pour rester distinct de `icloud.and.arrow.up` (Backup, `ProfileView.swift:144`) et de `arrow.down.circle` (Offline Storage) — les deux lignes vivaient alors côte à côte dans la section Management du hub. **Révision du 2026-09-16 : l'utilisateur a demandé un « cloud backup »** — le bouton porte donc `icloud.and.arrow.up`, le glyphe de sauvegarde du dépôt (même icône que la ligne Backup, `AppIntents.swift:29` et la Live Activity `BackupLiveActivityViews.swift:22`). La raison de la distinction a disparu avec le déplacement : les deux surfaces ne sont plus dans la même liste. L'upstream utilise `Icons.sync_outlined`.
- **Le comportement de `refresh()` quand le run est en cours.** `UploadViewModel.engine` est déjà observé par SwiftUI via `@Observable` ; `refresh()` ne sert qu'à recharger l'index hors-ligne (`offline.load()`). Si le premier rendu montre `offlineCount` à 0 le temps d'un frame, vérifier que la vue lit bien `offline.cachedAssets` (propriété observée) et non une copie locale. Vérifier par : `grep -n "cachedAssets" Sources/Features/SyncStatus/SyncStatusViewModel.swift`.
- **Le total d'un run terminé.** `engine.total` est remis à sa valeur du run courant et n'est pas conservé après un `reset()` ; si l'écran doit afficher « X sur Y » pour la **dernière** exécution et non pour la courante, la source est `lastRun` (`UploadHistoryEntry.uploaded` / `.total`, `UploadViewModel.swift:180-187`) et non l'engine. Vérifier par : `grep -n "uploaded: engine.uploadedCount\|total: engine.total\|UploadHistoryEntry(" Sources/Features/Upload/UploadViewModel.swift`.
- **La profondeur du lien vers les échecs.** Si `upload-detail` (bande AC-5040–5049) est implémenté avant cette fiche, la ligne « Failed » peut pointer vers son écran ; sinon elle reste une liste locale dépliée. Vérifier par : `ls Sources/Features/UploadDetail/` — absent aujourd'hui, donc le repli (liste locale) est le seul comportement correct à livrer.
- **Le libellé du volume hors-ligne.** `OfflineDownloadViewModel.formattedUsage(_:)` (`OfflineDownloadViewModel.swift:64`) est la seule mise en forme de bytes du dépôt pour cet écran ; `ByteCountFormatter.string(fromByteCount:countStyle: .file)` y est utilisé indirectement. Ne pas en écrire une seconde. Vérifier par : `grep -rn "ByteCountFormatter" Sources/Features/SyncStatus/`.
